# 1.0.8 构建与验证记录（2026-11-21）

## 问题

用户升级到 92% 后进度条不再变化，且磁力仍无速度。排查升级流程后确认：

1. **安装命令由正在运行的服务直接启动，没有任何超时与结果回读。** 92% 对应 `appcenter-cli install-fpk` 已启动。该命令可能等待运行中的应用让位/等待交互输入，而旧实现只在命令退出后才更新状态；命令不返回时界面就永远停在 92%。
2. **安装失败没有兜底。** 应用中心命令失败、超时、或设备上缺少可用的 appcenter-cli 时，旧实现只把安装包留在 `updates/` 目录，服务继续跑旧版本，用户看到的仍是 92% 或一条泛化错误。
3. **升级中断状态只在重启后处理，且缺少原因。** `logs/update.log` 只存在于设备上，界面上看不到安装命令的退出码或最后几行输出。
4. **磁力无速度的前提没有改变。** 升级没有真正完成，设备仍在运行 1.0.6（缓存种子无 tracker + DHT 被阻断），因此 1.0.7 的 tracker 修复并未生效。

## 变更

- 升级安装改为独立脚本 `updates/install.sh`（由服务以独立会话启动，随包生成）：
  1. 先把安装包复制到 `updates/unpack.<pid>/pkg.fpk`，避免新版服务启动后删除原包导致校验失败；
  2. `cmd/main stop` 先停掉应用，消除“安装命令等待应用退出”的死锁；
  3. `timeout 240 appcenter-cli install-fpk < /dev/null`，无 `timeout` 时用后台进程 + 240 秒轮询兜底；
  4. 解包 `app.tgz` 并逐字节比对 `mdm-fnos-server`，确认应用中心安装是否真正生效；
  5. 未生效时把包内 `mdm-fnos-server`、两个引擎二进制、`ui/`、`licenses/` 覆盖到应用目录（不触碰 `cmd/` 生命周期脚本）；
  6. 最后 `cmd/main start` 拉起应用；失败时把退出码与 `update.log` 末尾 12 行写入 `updates/install_error.txt`。
- 状态自愈：启动时只要当前版本已等于目标版本，无论上次停在 installing 还是 error，都标记为“已升级”；未完成时把 `install_error.txt` 的内容呈现到升级页。
- 服务端看门狗：仍处于 installing 超过 6 分钟且进程未被替换时，报“安装没有完成”，不再无限等待。
- 界面：安装阶段超过 4 分钟时停止轮询，提示重启应用或到应用中心手动安装。

## 本地实测

| 场景 | 结果 |
| --- | --- |
| 安装命令立即失败（退出码 1） | 脚本转入本地解包，`mdm-fnos-server` 被替换为包内 8,097,952 字节版本，随后调用 `cmd/main start`，无错误文件 |
| 安装命令挂起（超时从 240 秒缩短为 3 秒模拟） | 第 3 秒收到 rc=124，随后本地解包成功并拉起应用 |
| 覆盖范围 | 只写入二进制、`ui/`、`licenses/`，`cmd/` 保留原脚本，不产生多余的 `target/config` |
| 安装包被提前删除 | 脚本使用 `unpack.<pid>/pkg.fpk` 副本，解包不受影响 |
| 状态自愈 | 当前版本 == 目标版本时，重启后状态为 done（100%），并清理安装包与错误文件 |

`gofmt -l`、`go vet ./...`、`go test ./...` 通过；`tools/validate-fpk.py` 新增检查“升级脚本先停应用并限时安装”（`install_error.txt`、`timeout 240`）全部通过。

## 升级路径说明

- 设备上当前若停在 92%，该进程仍是旧版本，无法自行恢复：需要先在应用中心 **手动安装一次 1.0.8**。此后版本可正常应用内升级。
- 磁力资源本身若只由迅雷节点供源（如用户提供的 `292e1a6a…`），标准 BT 客户端仍无法获得迅雷的加速带宽；1.0.7 起界面会在 2 分钟无数据时明确提示。
